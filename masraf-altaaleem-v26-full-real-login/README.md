# مصرف التعليم — Starter SaaS

نسخة تأسيسية لنظام تعليمي تجاري متعدد المشتركين (Multi-Tenant) مع عزل بيانات على مستوى PostgreSQL RLS.

## الموجود الآن
- واجهة عربية متجاوبة.
- تسجيل/دخول عبر Supabase Auth.
- جداول tenants / memberships / classes / students / subscriptions / audit_logs.
- RLS لكل الجداول المكشوفة.
- منع تغيير tenant_id بعد إنشاء السجل.
- منع ربط الطالب بفصل من tenant مختلف.
- لوحة مشترك تبدأ بلا بيانات وهمية.
- لوحة مالك مبدئية.
- صفحة اشتراك جاهزة لربط بوابة دفع لاحقًا دون تخزين بيانات البطاقة.
- Headers أمنية أساسية عبر proxy.ts.

## التشغيل
1. أنشئ مشروع Supabase للإنتاج أو التطوير.
2. نفّذ ملفات SQL داخل `supabase/migrations` بالترتيب.
3. انسخ `.env.example` إلى `.env.local` وأدخل القيم الحقيقية.
4. شغّل `npm install` ثم `npm run dev`.

## مهم قبل الإنتاج
- لا تضع `SUPABASE_SECRET_KEY` في أي ملف Frontend أو متغير يبدأ بـ NEXT_PUBLIC.
- إنشاء tenant وmembership الأول يجب أن يتم من API/Edge Function موثوقة فقط بعد تحقق الحساب/الدفع.
- اربط بوابة دفع تدعم الاشتراك المتكرر وWebhooks مع تحقق من توقيع Webhook.
- أضف MFA لحساب المالك والإدارات.
- أضف Rate Limiting أمام نقاط التسجيل والدخول والدفع.
- اختبر RLS آليًا لحالات allow/deny قبل الإطلاق.
- اضبط CSP للإنتاج لإزالة `unsafe-eval` إن لم تكن مطلوبة، وأضف نطاق بوابة الدفع فقط عند اختيارها.

## سياسة مهمة
الواجهة وحدها ليست حاجزًا أمنيًا. العزل الحقيقي موجود في قاعدة البيانات عبر tenant_id + RLS، مع إبقاء مفاتيح الخدمة على الخادم فقط.

## رسائل أولياء الأمور
أضيفت قناة رسائل متعددة المستأجرين (WhatsApp / SMS). لا يسمح API بالإرسال إلا إذا كان الطالب تابعًا لنفس tenant للمستخدم الحالي، وكان رقم ولي الأمر موجودًا، وتم تسجيل guardian_consent. سجل الرسائل يحتفظ برقم مستلم مقنّع فقط، بينما رقم ولي الأمر يبقى في سجل الطالب الخاضع لـ RLS.

الإرسال الحالي يدعم Twilio من الخادم فقط. لا توجد محاكاة نجاح: إذا لم تضبط `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_FROM`, `TWILIO_SMS_FROM` و `SUPABASE_SERVICE_ROLE_KEY` فسيظهر أن المزود غير مهيأ ولن يسجل الإرسال كناجح.

بالنسبة للإنتاج في السعودية، يجب اعتماد Sender ID ومسار الرسائل المناسب لدى المزود والالتزام بمتطلبات الموافقة والتنظيم المحلية قبل تشغيل SMS تجاريًا. يمكن استبدال Twilio بمزود سعودي داخل `lib/messaging.ts` بدون تغيير نموذج عزل بيانات العملاء.

## V3 operational update
Added migration `005_operations.sql` with tenant-isolated attendance, tasks, task submission statuses, and teacher-to-class assignments.

New routes:
- `/teachers` — staff/role overview and class assignments data model.
- `/followup` — attendance + task tracking.
- `/messages` — individual and class-wide WhatsApp/SMS send workflows.
- `/api/messages/bulk` — server-side class messaging with tenant + consent checks and delivery logging.

The dashboard now uses the approved V4 mobile behavior: hidden off-canvas menu on phones, full-width content, tap-to-open navigation, and overlay/close behavior.

### Apply database updates
Run migrations 001 through 005 in order. Do not expose `SUPABASE_SERVICE_ROLE_KEY` in any client-side environment variable.

### Messaging safety
Bulk messaging only selects students in the authenticated tenant + selected class, with `guardian_consent=true` and a non-null guardian phone. Provider delivery status is written server-side; UI cannot mark a message as sent.

## V7 — لوحة الطالب مثل بنك الرياضيات

أضيفت بوابة طالب مستقلة على `/student/login` ولوحة الطالب على `/student` مع:
- بطاقة طالب مصرفية تعليمية تعرض الاسم، الصف، الرصيد، النقاط والمستوى من البيانات الحقيقية.
- كشف حساب وسجل عمليات الرصيد التعليمي.
- سجل نقاط التحفيز والتقدم بين المستويات.
- المهام وحالة التسليم والغياب والتأخر والملاحظات.
- التقييمات ومتوسط التقييم.
- إنجازات مشتقة من بيانات الطالب الفعلية، بدون بيانات تجريبية.
- لوحة شرف لأفضل الجهة وأفضل الفصل حسب النقاط الفعلية.
- الجوائز والروليت مع فرص مخصصة لكل طالب وسجل للجوائز.
- تحويل رصيد تعليمي بين الطلاب داخل نفس الجهة فقط؛ لا يسمح للطالب بإنشاء رصيد أو إيداع لنفسه.
- طباعة تقرير الطالب أو حفظه PDF من المتصفح.
- صفحة المعلم أصبحت تتيح إنشاء/إعادة ضبط حساب دخول الطالب وتحديد فرص الروليت.

### حماية دخول الطالب
حسابات الطلاب لا تُخزّن كلمات مرور نصية. تستخدم `scrypt` مع salt عشوائي، والجلسة تحفظ في Cookie من نوع HttpOnly وموقعة HMAC. بعد 5 محاولات دخول خاطئة يُقفل الحساب مؤقتًا 10 دقائق. جدول `student_portal_accounts` غير متاح مباشرة لأدوار anon/authenticated ويستخدمه الخادم فقط عبر Service Role بعد التحقق من الصلاحية.

أضف في بيئة الإنتاج:
`STUDENT_SESSION_SECRET` بقيمة عشوائية قوية لا تقل عن 32 حرفًا.

طبّق migration رقم `009_student_portal.sql` بعد migrations السابقة.
